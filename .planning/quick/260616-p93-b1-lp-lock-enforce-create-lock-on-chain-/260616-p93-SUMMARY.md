## What was broken

`listing_manager::list_token` Step 4 faked the LP lock:

```rust
let lock_id: u64 = listing_id;   // never called create_lock
```

A token could be marked `Active` with **no LP actually locked** — a direct
rug-pull vector. SubQuery/UI would then show the listing as locked when it wasn't.

## Part A — the fix (DONE, verified)

`Lunex/contracts/listing_manager/src/lib.rs`:

1. Added local mirror enum `LiquidityLockError` (same 7 variants, same order as
   `liquidity_lock::Error`) so the inner `Result<u64, _>` from `create_lock` is
   SCALE-decodable **without** a contract dependency — same technique as the
   existing `PSP22Error` mirror.
2. Replaced the Step 4 stub with a real `build_call` to
   `liquidity_lock::create_lock` passing the 8 positional args
   (owner=caller, pair_address, lp_token, lp_amount, lunes_liquidity,
   token_liquidity, cfg.lock_duration_ms, tier).
3. `lock_id` now binds from the call's return value → used in Step 5
   (`ListingRecord.lock_id` / `TokenListed.lock_id`); it is NOT `listing_id`.
4. **Atomicity:** the `?` short-circuits on lock failure (→ `Err(LockCreationFailed)`)
   **before** any insert/emit, so a failed lock cannot leave an orphan Active listing.
5. `#[cfg(test)]` comment block documents why the lock success/failure paths are
   e2e-only (Step 1 `transfer_from` precedes Step 4 off-chain).

### Compile bug fixed during continuation

The original executor (interrupted mid-task) left a type error: `try_invoke()`
with `.returns::<Result<u64, LiquidityLockError>>()` yields a **triple-nested**
Result (`env::Error` → `LangError` → `LiquidityLockError`) needing **three**
`.map_err(..)?`, but only two were written. It mis-copied the `PSP22Ref::transfer`
pattern, whose third `map_err` has no `?` because it's the function's tail return.
Fixed by adding the third `.map_err(|_| Error::LockCreationFailed)?` (bound to a
variable, so all three levels need `?`).
