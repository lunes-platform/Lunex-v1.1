<deploy_blocker>
## ⚠️ RELAYER FOLLOW-UP REQUIRED BEFORE DEPLOY (out of scope here, but MUST happen)

After this contract ships, the spot-api relayer is BROKEN-SAFE, not broken-unsafe:

1. The relayer currently watches `WithdrawRequest`. The escrow path NO LONGER emits it,
   so an un-updated relayer simply STOPS delivering native assets. Users' tokens sit in
   escrow and become reclaimable after the deadline. No funds are lost. This is intentional.
2. Before this contract is deployed to any environment serving real withdrawals, spot-api
   MUST be updated to:
   - watch the NEW `WithdrawQueued { id, owner, amount, deadline_block }` event,
   - deliver the native pallet-asset, THEN call `confirm_withdraw(id)` on-chain,
   - confirm WELL before `deadline_block` to avoid racing a user `reclaim_withdraw`.
3. SubQuery mapping impact: the indexer currently maps `WithdrawRequest`. It must add
   handlers for `WithdrawQueued`, `WithdrawConfirmed`, `WithdrawReclaimed`. `WithdrawRequest`
   is kept in the contract as a (now-unemitted) event so existing SubQuery decoding does not
   break; it can be removed only after the indexer is updated.

This plan does NOT modify spot-api or subquery-node. Record this blocker in the SUMMARY.
</deploy_blocker>

<reconciliation_note>
The spec's BREAK tasks B2-T5 say `confirm_withdraw` burns via `_burn(withdrawal.owner, ...)`
and B2-T6 reclaims by "reversing the escrow." Under transfer-to-self escrow (the locked
decision), the owner no longer holds the tokens — the CONTRACT does. So:
  - confirm_withdraw burns from the CONTRACT account: `_burn(self.env().account_id(), amount)`
  - reclaim_withdraw transfers from CONTRACT back to owner: `_transfer(self.env().account_id(), owner, amount)`
This corrects the spec's `_burn(owner)` wording. Total_supply is reduced exactly once, at confirm.
</reconciliation_note>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user → contract (request/reclaim) | Untrusted caller initiates escrow and reclaims own funds |
| relayer(admin) → contract (confirm) | Privileged caller burns escrow after off-chain native delivery |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-b2-01 | Spoofing | confirm_withdraw | mitigate | ensure_admin() — only relayer admin can burn escrow |
| T-b2-02 | Tampering | reclaim_withdraw | mitigate | NotWithdrawalOwner guard (caller == record.owner) + deadline gate |
| T-b2-03 | Repudiation | full lifecycle | mitigate | WithdrawQueued/Confirmed/Reclaimed events give on-chain audit trail |
| T-b2-04 | Elevation | reclaim before delivery | mitigate | reclaim gated by block_number >= deadline_block; relayer confirms before deadline |
| T-b2-05 | Denial of svc | escrowed funds trapped while paused | accept/mitigate | reclaim_withdraw intentionally NOT pause-gated → users always recover after deadline |
| T-b2-06 | Tampering | double-process (confirm+reclaim same id) | mitigate | record removed on first success → second call Err(WithdrawalNotFound) |
| T-b2-07 | Info disclosure | event topics leak owner | accept | owner address already public on-chain; no PII |
| T-b2-SC | Tampering | dependency installs | accept | no new crates added; reuses existing ink!/scale deps only |
